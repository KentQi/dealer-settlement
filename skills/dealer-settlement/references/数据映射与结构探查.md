# 数据映射与结构探查（阶段 0）

当客户的主档 / 三份导出与规范**表名、字段名、列顺序**不一致时，用本流程自动识别、经用户逐项确认后落盘映射，让引擎继续跑。**绝不静默猜、绝不修改三份源导出。**

## 何时触发

- 首次接新客户 / 换 ERP / 客户重发导出件；
- 引擎报 `[中止] 未找到含…的工作表` 或 `[自检未通过] 数据表未找到含…的列`；
- 用户说「表名 / 表头 / 列顺序不一样」「字段名不一致」；
- 主档六表被改过表名 / 列名 / 列顺序，导致 `load_master` 或引擎读不到。

无漂移时不要跑阶段 0（引擎原行为完全不受影响）。

## 漂移类型（`inspect_schema` 的 issue code）

| code | 含义 | 典型表现 | 处理 |
|---|---|---|---|
| `SHEET_NAME_MISMATCH` | 表名不同 | 「库存明细」vs 规范「库存」 | 映射 sheet |
| `FIELD_NAME_MISMATCH` | 字段名不同 | 「数量」vs「销售数量」 | 映射列 |
| `FIELD_ORDER_DIFF` | 列顺序不同 | 同名列但位置变 | 映射列序号；主档可用 `--fix-order` |
| `MULTI_CANDIDATE_SHEET` | 多张候选表 | 多个 sheet 都命中关键词 | **用户选一张**，禁止猜 |
| `MISSING_FIELD` | 规范字段找不到 | 缺「条码」等必填字段 | 必填缺失 → 阻断；补源文件或确认后映射 |
| `EXTRA_COLUMN` | 多余列 | 品牌 / 备注等 | 忽略，不影响计算 |

## 第 1 步：探查（只读）

```bash
# 目录模式：按文件名关键词自动判角色（master / jia / sales / inventory / next_month）
python3 "$SKILL_DIR/scripts/inspect_schema.py" "<客户根目录>" --out /tmp/探查.json --md /tmp/探查.md

# 单文件模式（不确定角色时显式指定）
python3 "$SKILL_DIR/scripts/inspect_schema.py" "<文件.xlsx>" --role jia --out /tmp/探查.json
```

- CLI：`inspect_schema.py <文件或目录> [--role master|jia|sales|inventory|next_month|auto] [--out 探查.json] [--md 探查.md]`。
- 纯只读、纯确定性、无网络；**发现漂移不退出非 0**（这是探查工具），文件不可读才 exit 1。

## 怎么读探查结果

| 字段 | 含义 |
|---|---|
| `role` / `path` / `sha256` | 判定角色、文件路径、文件指纹（记录当次文件供留痕；`apply_mapping` 不强制比对哈希） |
| `sheets[{name,rows,cols}]` | 实际工作表清单 |
| `header_candidates[{row,score}]` | 可能的表头行及得分 |
| `fields{字段:{found,score,confidence,alternatives}}` | 每个规范字段的匹配结果（`found` 为实际列名或列序号 / `null`） |
| `unmatched_fields` / `extra_columns` | 未匹配的规范字段 / 多余列 |
| `order_ok` | 列顺序是否符合规范 |
| `issues[{code,severity,detail}]` | 漂移问题清单（见上表） |
| `proposed_mapping` | 可直接编辑的 `_数据映射.json` 结构（下一节） |

置信度：**高 ≥ 0.85 / 中 ≥ 0.6 / 低 < 0.6**。高置信可建议采用；**中 / 低置信必须逐项问用户，禁止代替用户决定**。

## 第 2 步：向用户确认（话术模板）

逐项展示「实际名称 → 规范字段 / 置信度 / 影响」，低置信单独问。示例：

> 我在你的文件里发现以下结构差异，需要你逐项确认（我不会替你决定）：
>
> | # | 实际名称 | 规范字段 / 表 | 置信度 | 影响 |
> |---|---|---|---|---|
> | 1 | 挂账文件的工作表「未结算」 | 规范表「挂账」 | 高 | 决定读哪张表 |
> | 2 | 列「数量」 | `qty`（未结算数量） | 中 | 期末结存与差异 |
> | 3 | 列「金额」 | `amount`（未结算金额） | 低 | 期初货值 |
>
> 请逐项回答「采用 / 不采用 / 改成哪个」。第 2、3 项置信度较低，请重点确认。

- 用户回答后，把裁决结果写进映射 JSON（`notes` 记理由）；
- 确认人必须落到 `confirmed_by`，写入时与 `--confirmed-by "<姓名>"` 一致；
- **禁止**在用户未表态时自行采用低置信映射。

## 第 3 步：映射 JSON 结构

schema `dealer-settlement/data-mapping@1`（`inspect_schema` 的 `proposed_mapping` 必须同构）：

```json
{
  "schema": "dealer-settlement/data-mapping@1",
  "confirmed_by": "<确认人姓名>",
  "confirmed_at": "<ISO8601>",
  "notes": ["挂账表实际名为「未结算」，经用户确认映射到规范表"],
  "master": { "sheets": { "实际表名": "规范表名" } },
  "order": ["主体", "合同", "价格", "SKU", "期间", "贴花"],
  "sources": {
    "jia": {
      "sheet": "未结算",
      "header_row": 3,
      "columns": { "name": "商品", "qty": "数量", "amount": "金额" }
    },
    "sales": {
      "sheet": "销售流水",
      "header_row": 1,
      "columns": { "bar": "条码", "qty": "销售数量", "date": "销售日期" }
    },
    "inventory": {
      "sheet": "库存明细",
      "header_row": 1,
      "columns": { "bar": "条码", "qty": "库存数量" }
    }
  }
}
```

- `columns` 的值可以是实际列名或**列序号（从 1 起）**；缺失字段不要瞎填；
- `sources.<role>.file` 可选：显式指定该角色的文件名（不放该字段时按关键词发现）；
- `sources.<role>.next_month` 与 `sales` 同构（可选，用于"库存+次月已销"表）；
- `master.sheets` 只记录实际表名 → 规范表名；`order` 是主档表顺序（配合 `--fix-order`）；
- 文件位置固定：`<客户根目录>/_数据映射.json`。

## 第 4 步：预览与落盘

```bash
# 4.1 dry-run（默认）：重新核对每个 sheet / 列在当前文件中真实存在，打印将写入内容与影响
python3 "$SKILL_DIR/scripts/apply_mapping.py" "<客户根目录>" "<映射.json>"

# 4.2 用户确认后落盘
python3 "$SKILL_DIR/scripts/apply_mapping.py" "<客户根目录>" "<映射.json>" \
    --write --confirmed-by "<确认人>"

# 4.3 重跑对账（B1 / B2）验证映射生效
```

- `--write` **必须**带 `--confirmed-by`，否则 exit 1（提示「必须经用户确认」）；
- 写 `_数据映射.json`，副本归档 `_确认记录/映射_YYYYmmdd_HHMMSS_mmm.json`；
- dry-run 发现映射指向不存在表 / 列 → 中文报错 exit 1，不写盘。

## 主档修复（可选）

主档本身表名 / 列名 / 顺序漂移时，可让脚本按规范修主档（**先 dry-run，再确认，再备份写入**）：

```bash
# 先看修复计划
python3 "$SKILL_DIR/scripts/apply_mapping.py" "<客户根目录>" "<映射.json>" --fix-master [--fix-order]

# 用户确认后执行
python3 "$SKILL_DIR/scripts/apply_mapping.py" "<客户根目录>" "<映射.json>" \
    --fix-master [--fix-order] --write --confirmed-by "<确认人>"
```

规则：只改表名→规范名、列名→规范列名、可选按规范顺序重排；保留原有值 / 格式 / 列宽；写前备份到 `_备份/`（毫秒时间戳），再原子替换；**永不修改三份源导出文件**（源侧只写映射）。

## 引擎如何使用映射

- `load_master.py`：客户根目录存在 `_数据映射.json` 时读入并放进 `RECON_CFG['mapping']`；映射文件损坏 → 中文报错 exit 1；不存在 → 行为与旧版完全一致（向后兼容）。
- `recon_engine.py`：有 mapping 时按映射选工作表 / 表头行 / 列（显式优先于关键词启发）；映射指向的表 / 列不存在 → 明确中止并指出是哪一项；无 mapping → 现有逻辑不变。
- 改映射后必须**重跑 B1**：旧 `RECON_CFG` 不含 mapping，引擎仍按旧行为。

## 常见错误

1. 未经用户确认就 `--write` → 违反确认门禁；必须先 dry-run 展示再确认。
2. 低置信项自己拍板 → 禁止；必须逐项问用户并在 `notes` 留理由。
3. 映射指向不存在的表 / 列 → dry-run 会报错；修映射或换文件。
4. 映射与源文件版本不一致（客户重发导出）→ 重新 `inspect_schema` 核对表 / 列是否仍成立；探查报告里的 sha256 只是当次文件指纹，`apply_mapping` 不做强制哈希校验，换文件不会自动拦截。
5. 手工乱改主档表名 / 列名 → 用 `--fix-master / --fix-order` 修复，不要手改（易漏表头 / 顺序）。
6. 把「映射确认」当成数据正确性背书 → 映射只描述对应关系，错误映射仍会产出错误结果（见 SKILL §12）。
